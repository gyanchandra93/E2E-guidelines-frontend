Understanding the E2E Test Plan Guidance

The person is basically giving guidance on how the team should prepare E2E test plans before writing Playwright tests.

1. Don't immediately start writing Playwright code

The author says:

“before we start writing E2E tests ... please put together a test plan for each ticket”

Meaning: For each feature/ticket, first decide what exactly needs to be tested.

Don't jump directly into Playwright code such as:

test("should ...", async ({ page }) => {
  // Playwright code
});

First create a small test plan.

2. They want one test plan for each ticket

Suppose you have two tickets:

  • Ticket A → Add a new custom field
  • Ticket B → Add image upload functionality

Ticket A – Test Plan

  • User can add a custom field.
  • Custom field appears in the table.
  • User can edit the field.
  • User cannot save when required information is missing.

Ticket B – Test Plan

  • User can upload an image.
  • Supported image formats work.
  • Unsupported formats are rejected.
  • User can delete the image.

Only after this should you write the Playwright tests.

3. Base tests on a real user action → expected outcome

This is probably the most important part of the message.

They give an example:

“creating a customer should queue exactly one welcome email with the expected recipient and subject.”
User does something → System should produce a specific result
Action:
Create a customer

Expected result:
Exactly one welcome email is queued

And:
- Email goes to the correct recipient
- Email has the correct subject

They don't want vague tests like "Check that customer creation works." They want something measurable and specific.

4. Include dependencies and setup requirements

The test plan should explain setup, dependencies, and cleanup.

Setup:
- User must be logged in
- Project must already exist
- Test data must exist

Test:
- Create customer

Expected:
- Customer appears in the list

Cleanup:
- Delete the test customer

This helps another developer understand how to run the test.

5. Think about negative scenarios too

Don't only test the happy path. Think about what should happen and what should not happen.

Happy path

User uploads a PNG
        ↓
Upload succeeds
        ↓
Image appears

Negative path

User uploads an unsupported file
        ↓
Upload should fail
        ↓
Error message should appear
        ↓
Image should NOT be added

The negative test is important because it can catch regressions.

6. Pay special attention to permissions and filtering

The author specifically mentions permissions or filtering.

User without edit permission:

Expected:
- Edit option should not be available
- User should not be able to modify the field

For filtering:

Apply filter: Status = Active

Expected:
- Active records are displayed
- Inactive records are NOT displayed

So the E2E tests should verify business rules, not just whether buttons can be clicked.

7. Capture the reasoning before coding

The author says:

“Please capture that reasoning in the tickets before coding”

This means the Linear ticket itself should contain the test plan.

E2E Test Plan

1. Given a user with edit permission
2. When they open the Test Checklist
3. And update the Serial Number field
4. Then the updated value should be displayed

Negative scenario:
5. Given a user without edit permission
6. Then the field should not be editable

Another developer should be able to look at the ticket and understand: "These are the behaviors our Playwright tests need to prove."

Why are they asking for this?

The author wants to avoid tests that are simply:

click button
click button
fill textbox
expect something

without knowing what behavior the test is supposed to protect.

Business requirement → Test scenario → Expected behavior → Playwright implementation

In one sentence

The author is saying:

“Before writing Playwright code, clearly define what user behavior we're testing, what should happen, what should not happen, what setup is required, and what regression the test is protecting against.”

One important distinction

The test plan is not the Playwright code itself. It is the blueprint from which you later write the Playwright test.

Test Plan → Playwright Test → Automated E2E Test
